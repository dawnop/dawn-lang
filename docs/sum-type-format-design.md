# 和类型首竖线的格式化约定

> 状态：**current**。记录 issue #74 的和类型格式化约定及验证。

解析器的 `type_decl` 已接受首构造器前有或没有 `|`，但规范示例和源码
混用两种单行拼写。只扫源码会再次漂移，因此约定交给 `dawn fmt`：单行
声明去掉首竖线，多行声明保留作者的构造器换行与竖线；解析接受范围不变。

格式器目前只要求词法分析成功，不要求整份源码能解析。实现继续遵守这个边界，
在 token 流识别 `type Name[参数] = | Constructor`，仅当声明位于同一物理行
时过滤那一个首竖线。物理行从源码跨度判断，不能依赖 NEWLINE token：词法器
会吞掉等号、竖线和括号内部的换行。下一行的后续构造器及 derive 也算多行。
匹配分支、效果联合、字符串和注释里的竖线不在这个识别路径里。
识别限定顶层的普通 `type`，排除 `opaque type` 和 trait/impl 内的关联类型：
它们的等号后不是构造器列表，不能把原本不合法的首竖线误删成合法的类型绑定。

验证覆盖单行、泛型、注释、多行字段与构造器、模式分支、幂等性和词法拒绝。
规范中英文同步，树内源码用格式器改写；std 嵌入源码由生成器刷新。诊断 golden
只通过正式录制器更新，逐项核对文本、顺序不变，仅位置随源码移动。Core 也用
正式脚本重录和检查。实际父提交与修复版的 fmt/emit 输出比较决定精确的
`Emit-Change` 声明，不借已有声明推断差分不存在。

在父提交 `5c6c3171` 的源码上实测：父格式器与修复版有 49 个文件不同，差异为
68 个单行首竖线；其中 std 7 个、packages 2 个、examples 1 个、门禁语料 58 个。
语料原本用于测试的其他空白不改，正式源码根目录完整运行格式器。父编译器和修复版
编译同一份当前源码，十个 JVM emit 语料逐字节相同；因此仅声明 `Emit-Change(fmt)`。
对比已经规范化的树时，上一个 release 的 fmt 差分本身没有变化，这不能代替前述
未规范化父树的对照。

三组新增测试覆盖 CRLF、无尾换行、相邻声明、泛型括号、多行字段、注释、derive
及非 ADT 边界。在独立临时源码中换回父版格式器、只保留新增测试，598 项中恰好
两个单行规范化测试失败，其余 596 项通过；修复版 598 项全部通过。标准库 152 项、
compiler-plan 64 项通过。

checker 正式录制和复检为 146 个 case、581 条诊断。只有
`scripts/checker-corpus/cases/public_surface.expected`（18 条）与
`public_surface_import.expected`（1 条）移动绝对字符位置：按源码每次删除的
两个字符逐项回算，消息、提示、顺序和行号均未变化；其中一条字段诊断的两端列号
各减少 2，其余列号不变。导出表面契约全部正常断言及 `recurse-adt-fields` 负控、
三个 opaque 对照和 15 个修改过的 JVM/native/ASan 语料通过；手写 `.expect` 不改。

Core 官方重录和检查为 17 份完整转储、87 个模块哈希。规范化哈希只移动
`front.fmt`、生成的 `embed.stdsrc` 和 `compiler_plan.exitmem`；最后一个实测只有
成对 handler ID 从 27952 移到 27979。父版和修复版编译同一份当前源码，所有 Core
转储也逐字节相同。自举固定点 B == C、格式检查及文档和 gate-map 门禁通过。

上述计数与 handler ID 是 `5c6c3171` 上的独立修复验证。整合前序
`240d275f` 时，保留 T3 把 `I64` 从 tileir/dev 移到 std/gpu 的改动，并用格式器
处理它新增的六个标记类型。相对此前序，最终源码迁移为 73 个首竖线：std 13 个、
packages 1 个、examples 1 个、门禁语料 58 个；嵌入 std 与 Core 再由正式工具生成。
`std/gpu.dawn` 与 `packages/tileir/src/dev.dawn` 属于 GPU ledger 的摘要范围，
即便这次没有语义变化，旧 ledger 也不能沿用，必须在最终源码固定后正式重跑。

不做的：不修改 parser，不强制给缺少首竖线的多行声明补竖线，不折叠或展开
声明，不改效果联合或模式分支；这些都超出已有语法的单行规范化。
