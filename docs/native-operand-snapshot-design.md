# native 操作数的值快照

> 状态：**current**。issue #84 的 native 操作数值快照与引用生命周期修复。

## 问题与根因

issue #84 的两参数调用先读局部整数，再在后一个参数的块中修改同一绑定；
在父提交 `4963ca91` 上，同一编译器的 JVM 答案是 21，native 却成功退出并输出 31。
生成的 C 先写回变量，随后调用参数才读该变量。规范要求从左到右求值，
不是所有参数的副作用执行完后再读取前面的变量。

代码检查定位到 C 发射器的 `atom_expr` / `emit_ordered`：局部读取可原样内联，
只有至少两个非原子操作数才提升表达式。这里把「读取不运行代码」当成了
「值不会被后续代码改变」。后续块的语句先被发出，调用参数里留下的局部名字
因此读到新值。只提升 C 指针还不够：借用引用的源绑定被赋值时会释放旧值，
快照还必须持有旧对象直到调用结束，或在后续操作数提前退出时释放它。

## 实现与边界

在 native RC 的操作数改写处识别后续操作数对前面已引用绑定的赋值。
复用已有的完整 Core 赋值遍历，不以顶层语句或源码文本猜测。
发生冲突时沿用 `intr_args` 的从左到右临时绑定、拥有/借用位置、临时引用
存活集合与提前退出清理；标量也形成值快照。拥有参数、构造器、元组、列表
和闭包捕获使用同一条受冲突约束的路径。动态调用目标属于第一个操作数，
其快照与参数一起拥有明确的生命周期。

没有冲突的操作数保留旧路径，短路和条件分支仍只在原来的分支内求值。
引用快照只保留对象身份，不深拷贝可变容器，不改变容器自身的可见修改。
实现落在 `selfhost/src/c/rc.dawn` 及 native 差分语料；C 发射器只补充前置条件
说明，没有另放一条不负责引用计数的指针快照路径。

## 验收

同一父编译器运行最终 17 行回归，JVM 与手写期望全部一致，native 有 13 行错误。
修复后整数、浮点、布尔、引用与投影、动态目标、容器构造、条件/循环内赋值
以及 return/break/continue 全部匹配预期，ASan 和泄漏检测通过。
完整 native 差分的 128 个条目及附带的文件删除契约/编译型负控全部通过，
包括 #68/#80 的原有 RC 与循环跳转语料。

新增四个内联测试检查冲突分类、标量暂存、拥有/借用引用和动态目标提前返回；
selfhost 共 610 项、Planner 64 项通过。JVM 与 native 自举固定点均为 B == C，
并通过各自独立运行 smoke。

Core golden 仅通过官方脚本 record/check，17 份完整转储、88 个模块哈希通过。
规范化变化限于 `c.rc` 和受声明编号位移影响的 `compiler_plan.exitmem`；
没有修改 Core 的过滤规则。真父编译器与修复后编译器编译同一份新源码时，
十个正式 JVM emit 语料逐字节相同，因此没有新增 `Emit-Change` 声明。

## 不做的

不改变语言求值顺序，不修改 JVM 已落地的 #80，不扩大引用计数运行时协议，
不深拷贝引用，不同时修复函数值参数上限 #87 或 Playground tokenizer #83。
后两项由同一作者在独立后续任务中处理，不使用 subagent。
