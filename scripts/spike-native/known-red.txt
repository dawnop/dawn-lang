# Checks that fail today. run.sh treats a listed failure as non-fatal and an
# unlisted one as fatal -- and it also fails when a *listed* check starts
# passing, so a fix cannot leave its entry behind.
#
# One check is listed, at the bottom: case folding, which the two backends
# answer differently. Everything else compiles with both backends, runs with
# both, and agrees with a written expectation.
#
# It is worth saying what that does and does not mean. It does not mean the
# native backend is finished -- it means the *corpus* no longer catches it out,
# and the way to keep this file honest is to add programs, not to keep entries.
# When these corpora were added on 2026-07-25 four of the entries turned out to
# be semantics Core did not carry, so each consumer had invented one, and the
# harness had been admitting only programs both backends already agreed on;
# that is how they stayed invisible. Each closure below records what was
# actually wrong, at the section its entry was in.

# --- equality -------------------------------------------------------------
# Closed by the structural expander (semantics-closure-design.md 3): lowering
# spells the comparison out over the type's own structure, so both backends
# compile one definition instead of inventing one each. eq_adt:native,
# eq_adt:diff and eq_bytes:jvm were deleted here.

# `bytes_* has no native implementation` was here. The C runtime implements
# the whole bytes family now, and the emitter reaches it from the intrinsic
# table rather than a hand-written arm. Two defects the refusal had been
# hiding came out with it, both silent: `++` at Bytes emitted the *string*
# concatenation, and `==` at Bytes compared pointers, so two content-equal
# arrays were unequal. eq_bytes:emitc was deleted here.

# `derive Ord` was here: its body was written straight to JVM bytecode, so
# Core never carried it and the C backend emitted a *call* to
# `impl$0$Adt<n>$cmp` with no definition -- an undefined symbol and no
# diagnostic at all. No corpus covered `derive Ord` until 2026-07-26, which is
# why that stayed invisible. Closed by lowering the comparison the way the
# structural equality already was, so both backends compile one definition:
# ord_derive:cc was deleted here.

# --- rendering ------------------------------------------------------------
# show_derive:emitc was here. Show was not a trait but three things wearing
# one name -- an AdtI flag, a checker predicate, and an instanceof chain in
# dawn/rt/Show -- and a tagged union has no arm in that chain, so it fell
# through to the `toString` the JVM emitter wrote directly as bytecode. Core
# carried neither end. Closed by lowering the rendering over the type's own
# structure the way equality and ordering already are
# (semantics-closure-design.md 6), so both backends compile one definition.
#
# The container half was here for a reason that has since been replaced. It
# used to be that `show` at a List/Map/Set reached the runtime intrinsic and
# native had no runtime to reach; std carries `impl[T: Show] Show[List[T]]`
# now, so rendering goes through the same synthesised bodies show_derive.dawn
# does.
#
# `emitc` and then `cc` were the wall, and neither is now. The C runtime
# implements the intrinsic contract, so std compiles into the translation unit
# and `std/pvec.of_array` and std's own `show` bodies have definitions.
#
# Linking std in is what made four silent miscompiles visible, all of them in
# the erasure boundary the JVM gets free from its verifier and from
# LambdaMetafactory: a tuple stored its fields natively and `map_from` read
# them back as pointers; a list literal pushed unboxed elements; a closure
# adapter carried the lambda's concrete types where every caller casts to the
# erased shape; and an impl was named by its instantiated subject at the call
# site and its generic one at the definition. Each compiled. show_containers:cc
# was deleted here.

# A bound whose subject *contains* a rigid variable rather than being one
# (`[T: Eq]` used at `Option[T]`) was here. It reached the `struct_eq`
# intrinsic -- a runtime structural walk the JVM has (Object.equals, which an
# `impl Eq` takes over) and native does not. Closed by building the whole's
# dictionary out of the parts' (trait-v2-design.md 3.8) instead of walking:
# eq_generic:emitc was deleted here.

# --- dictionaries ---------------------------------------------------------
# Closed by making the table the only answer to "which dictionary is this"
# (semantics-closure-design.md 5): lowering gives every slot a real function
# to name -- synthesising one where neither an impl nor a trait default
# supplies it -- and both backends build their dictionary from that table.
# dict_forward:cc was deleted here.

# --- comptime -------------------------------------------------------------
# const_fold:jvm was here. interp.dawn rendered every non-scalar as the literal
# "<value>", so a const holding `to_string` of an ADT folded to the wrong
# string -- on the JVM, in the backend that ships. This is the check .expect
# exists for: both targets fold at compile time, so they agree with each other
# and a differential comparison alone reports ok.
#
# Closed in two halves. Rendering became a Core body, so the interpreter has
# the same definition the backends compile; and the interpreter learned to
# dispatch through a dictionary, which is what a rendered container reaches
# once std carries `impl[T: Show] Show[List[T]]`. It refused before, which
# would have turned the wrong answer into a compile error rather than a right
# one.

# `Comptime consts are not emitted for native yet` was here. The emitter reads
# the folded values now, from the same per-module view the JVM path builds --
# a const is named by its simple name, so std/pvec's MASK and std/hamt's MASK
# are two constants and the map cannot be global. A value that folded to
# something structured still refuses, and says so: C has no `<clinit>` to
# rebuild one in. const_fold:emitc was deleted here.

# --- hashing --------------------------------------------------------------
# hash_key:jvm and hash_key:emitc were here, for one day. `hash` was the last
# member of the eq/ord/show family lowering still handed over as a bare
# intrinsic whatever the subject was, so each backend answered for itself; no
# corpus had hashed a tuple or a union until the one that found this.
#
# The JVM's answer for a constructor with no fields was the identity hash of
# the singleton instance -- the class writes no hashCode, so it inherited
# Object's. That is not a function of the value: two programs got different
# numbers for the same `Origin`, and a `(Origin, 1)` folded one of them in.
# The tag was absent too, while `==` and `cmp` both consult it. Past the
# scalars native had nothing at all, and no hash for Bytes either, which is a
# hash scalar the C runtime had never grown one for.
#
# Closed the way the other three were: lowering spells the fold out over the
# type's own structure, so both backends compile one definition
# (semantics-closure-design.md 3).

# --- the two barriers -----------------------------------------------------
# catch_kinds:native, catch_kinds:diff and catch_kinds:jvm were here, for one
# day. `java_try` is what std/io wraps a throwing primitive in; `catch_panic`
# is the catch-all. On the JVM the difference is the class hierarchy: `panic`
# throws an `Error`, and `java_try` catches `Exception`. Native has no
# exceptions -- everything arrived through one `longjmp` -- so the two
# intrinsics were literally the same function, and `java_try` caught every
# panic the JVM lets through. Every line of the corpus that raises a Dawn
# failure disagreed.
#
# Closed by giving a native failure a kind, which is what the JVM gets from
# its class hierarchy for free: a handler records whether it takes panics, and
# a raise walks to the innermost one that will. The io primitives raise a
# fault; everything else in the C runtime is the language's own failure and
# panics.
#
# Two more the same file found, one on each side, both closed with it:
#
#   * `std/bytes.slice` documents "both ends are clamped and `start > end`
#     yields empty, so this never panics". The JVM did that. The C runtime
#     panicked -- directly under a comment saying it clamped like the JVM.
#     Not about catching at all: two answers to the same call.
#
#   * `from_code_points` with an out-of-range code point was the one place a
#     *host* exception still escaped on the JVM: `StringBuilder.appendCodePoint`
#     throws `IllegalArgumentException`, so the io barrier caught an argument
#     error the way it catches a missing file. It panics now, the way a bad
#     index does.

# --- case folding ---------------------------------------------------------
strings_case:jvm
strings_case:native
strings_case:diff
#
# The two backends answer `str_lower`/`str_upper` differently, and neither
# answers what strings_case.expect asks for. The JVM does *full* case mapping
# (`String.toUpperCase`): `ß` becomes `SS`, so the code-point count is not
# preserved. The C runtime folds ASCII only, so every cased letter above U+007F
# is left alone. Each was written to look like the obvious implementation on
# its own platform, and neither is a function the other can implement.
#
# The expectation is *simple* mapping -- one code point in, one out. It is the
# only version of this operation two backends can implement from one table:
# full mapping is locale- and context-sensitive, so it belongs in a library
# that can take a locale rather than in a primitive.
#
# The comptime half is in the same file. A `const` is folded on the compiler's
# host and a live call runs on the target, so `str_upper` gives a different
# answer today depending on whether the expression was written `const`. That is
# what makes this a semantics defect rather than a missing feature: one
# operation with two definitions, and the fold reaches only one of them.
