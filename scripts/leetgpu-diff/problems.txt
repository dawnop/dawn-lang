# The leetgpu ledger: which of https://leetgpu.com/'s problems this backend
# can solve today, and with what. One line per problem, appended as a knife
# lands; check.py is the gate that keeps it from being a claim.
#
#   <id> | <title> | <kernel> | <reference> | <corpus> | <tier>
#
#   id         the problem's id on leetgpu.com (and in AlphaGPU/leetgpu-challenges)
#   kernel     the kernel scripts/tile-golden pins under that name: it must
#              have a .mlir and a .tilebc golden, be in run.sh's kernel list
#              and be traced by kernels.dawn. Since knife 16 this may be
#              SEVERAL kernels joined with `+`, because a problem can be a
#              sequence of launches: 85 is three, 84 is four launches over
#              three. The set has to be exactly what the corpus runs, which
#              is the layer-2 program's own `sequence_kernels()` list
#              rather than anything written here
#   reference  the hand-written host reference the fake device answers with,
#              as <module>.<function>; it must exist there. It is the second
#              opinion, never the kernel's own code path. One per kernel,
#              joined with `+` in the same order, since each launch of a
#              sequence has its own second opinion (the same reference may
#              appear twice: a product is a product)
#   corpus     the layer-2 program and case that runs the kernel on the GPU
#              against that reference (<program>:<case>)
#   tier       exact     -- bit for bit, every lane, no tolerance
#              tolerance -- an atol/rtol claim, for a kernel whose operations
#                           are not IEEE-exact: the transcendental functions,
#                           and `mmaf`, whose summation over K has no
#                           specified order
#
# Two problems share one kernel where the problem is the same computation
# over a different shape: a matrix is a vector to a kernel that reads it
# flat, so 8 (Matrix Addition) is 1 (Vector Addition) and nothing more.
#
# A kernel is recorded for ONE shape, and the row names the problem it
# solves at that shape: a convolution with three taps over a 40 by 36 image
# is 2D Convolution, and another shape is another recording of the same
# kernel, not another mechanism.
#
# The count of a Count Element problem does not change with the number of
# indices the caller reads its buffer with, so 43, 44 and 45 are one kernel
# over a flat run of elements, the way 1 and 8 are.
#
# Two problems share one reference where the reference does not depend on
# the format: `matmul_ref` is a triple loop that rounds to the output
# buffer's format, so it is the second opinion for an f16 product and an i8
# one as much as for an f64 one. The KERNELS differ, and the corpora do.
#
# 85 of the 97 reachable problems (41 Simple Inference is a PyTorch exercise
# and out of range). The plan that orders the rest is the cuTile coverage
# memo; knife 7a is the boundary knife, 7b the reduction one, 8 the
# two-dimensional one, 9 the strided one, 10 the integer one, 11 the wide
# one (more than one output buffer, in place, and the f16 / i8 / u8 formats)
# and 12 the indexed one (an address a lane computes, or reads out of a
# buffer, rather than one the strides fixed at recording time) and 13 the
# prefix one (an operation that keeps every intermediate accumulator, and
# the first whose region body is allowed not to commute) and 14 the atomic
# one, which adds exactly this: 13 Histogramming is the only problem in
# range that needs two lanes to be allowed to name one element, and 15 the
# composed one: it adds NO operation at all. Tile IR has no `erf`, so
# `tileir/dev.erf` is Abramowitz-Stegun 7.1.26 written out of the
# arithmetic already there, and 65 is the one problem that asks for one, and
# 16 the multi-launch one: it adds no operation either, only a way for the
# HOST to say "these launches, in this order, over these buffers" and a
# verdict that holds one, and 17 the second multi-launch one, which adds no
# operation either: what it adds is the observation that an attention
# variant is a RULE ON A SCORE, so four of its six problems are one kernel
# each and hand their scores to the softmax and the context product knife 16
# recorded. That is what the last eleven rows below are, and what the
# sixteen problems still out of range for that reason need, and 18 the
# spending one: it adds no operation, no mutant and no mechanism at all.
# Seven of its eight problems are single launches that every knife from 7a
# to 12 had already made possible and nobody had written; the eighth
# (leetgpu 12) is the attention family with a HEAD, which is a column
# slice, which is a base offset and a row stride. So the eight rows it adds
# are what "the mechanism exists" was worth once somebody spent it, and
# that number is worth having beside the mechanism knives.
#
# A kernel is recorded for one shape and a row names the problem it solves
# at that shape, which for the knife-12 rows means small ones: `sort_rank`
# sorts 32 values with 32x32 comparisons and `merge_rank` merges two runs of
# 32 the same way. Both are O(n^2) in comparisons, which is what a machine
# with tiles and no shuffle does in ONE launch; the O(n log n) shapes need
# several launches and a host loop between them.
# ONE ROW CAN BE RECORDED SMALLER THAN THE PROBLEM. Every row above names
# a problem whose dimensions its caller chooses, so the shape a kernel was
# recorded at is a shape the problem has. Knife 21's two rows are the first
# that are not: leetgpu 74 IS GPT-2 124M (D = 768, 12 heads, FFN 3072) and
# leetgpu 93 IS a 512-wide Llama block (8 query heads over 2 key heads, FFN
# 1408), and both are recorded here at a reduced model -- 64 tokens of 64
# and of 128 features, 2 and 4 query heads, feed-forwards of 128 and 64.
# What that costs and what it does not: a recording constant in
# kernels.dawn is a loop bound and a stride, so the same kernels at the
# published constants are the same programs and the grid is the caller's;
# what cannot be scaled is the SECOND OPINION, which is a hand-written host
# reference over a `List[Float]`, and GPT-2's weight buffer alone is seven
# million of them. So these two rows claim the block's structure at a shape
# a host reference can answer for, and not that a 124M block has been run.
# A reader who wants the stronger claim should read it as the mechanism and
# not the model.
