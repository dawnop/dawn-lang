# 操作数临时引用的提前返回清理

> 状态：**current**。记录 issue #68 的操作数临时引用修复（正文），#467 的
> 强制 unwind 一半（§二），以及 #482 的分配先于会 raise 的实参（§三）。

`out = out ++ [get(h)?]` 的第一个操作数由 `intr_args` 提升到临时绑定。
旧 `out` 可以转移给它，但临时绑定没有登记进 RC 作用域，因此第二个操作数
内的提前返回看不到它。消费检查器报告返回时还有活跃绑定。

实现是在求值后续操作数期间登记已提升的引用，并将这些引用加入后续操作数的
存活集合，避免普通语句清扫提前释放。操作数全部求值后，从作用域账本移出它们：
借用位置由现有包装器释放，拥有位置交给调用者。返回、break 和 continue
沿用现有作用域展开。没有新语法，也不改变 JVM 后端。

落点是 `selfhost/src/c/rc.dawn` 的操作数改写与消费检查测试，以及
`scripts/spike-native` 的成功、失败路径回归。验证包括修复前的负控、JVM/native
输出对拍和开启泄漏检测的 ASan，Core golden 只用正式脚本重录。

已验证：同一回归在修复前的 JVM 打印预期结果，而 native 编译在直线赋值和循环
赋值两处均报告返回遗留绑定；修复后 `spike-native/run.sh` 的对应条目全部通过，
包括非空堆列表上的失败路径。内联 RC 测试同时覆盖被提升的第一个操作数为拥有
和借用参数的两种调用模式，以及后续操作数中的正常语句清扫。

`dawn test selfhost` 594 项通过；源码循环标签与 Map 复用契约及其变异负控通过，
复用契约的正常直接更新与记录更新两条路径仍为 100%。Core 正式重录与检查通过
（17 份完整转储、87 个模块哈希）。除 `c.rc` 外，`compiler_plan.exitmem` 的
规范化哈希也移动：前面声明增长改变了生成的成对 handler ID 整数。
用父提交 `85e10bc7` 编译器和修复后编译器编译同一份源码，十个正式 JVM emit
语料逐字节相同，因此没有新增 `Emit-Change` 声明。

不做的：不改变赋值的最后使用转移优化，不把标准库已有递归绕行改回循环，
不扩展运行时清理协议；这里缺的是编译器已经生成的临时绑定的作用域归属。

## 二、强制 unwind 时为顺序提前求值的 owned 操作数（#467，2026-10-04）

#68 管的是 RC pass 自己提升出来的临时绑定，在**正常控制流**的提前返回上漏掉。
#467 是另一半：C emitter 的 `emit_ordered`（`selfhost/src/c/emitc.dawn`）为了钉住
求值顺序，把一行里会跑代码的操作数逐个绑成 C 临时变量。消费位上的那一个已经是
owned 引用，要等整行求完、构造器或被调函数接手才算交出去；在这之间它只是一个
普通 C 局部，不在 `dawn_own` 槽里。后一个操作数 panic，或者挂起后 continuation
被丢弃，帧都由强制 unwind 丢掉，而 unwind 只释放槽（native-failure-design.md
刀 3、`dawn_rt.c` 的 "THE SECOND EXIT, AND PERCEUS"），这个引用就漏了。那一节末尾
「残留」记的「未具名的中间值」就是它，当时语料里没有这个形状。

### 2.1 两个候选与裁决

审计给了两个落点：

1. **emitter 侧分槽**：消费位、引用类型、且后面还有会跑代码的操作数时，结果直接
   写进一个新的 `dawn_own` 槽，在构造或调用处用 `dawn_take` 交出。
2. **RC 侧绑成 tracked 符号**：让 `consume_all` 也像 `intr_args` 那样把这些操作数
   `CSLet` 出来，`bind` 进作用域，在使用点 transfer。

裁 1。理由：

- **漏洞在 emitter，不在账本。** RC pass 的 Core 里根本没有这个临时变量：
  `consume_all` 的常规路径不提升任何操作数，提升是 emitter 为 C 的未定求值顺序
  补的。Core 语义下操作数是从左到右求值、整行交给接收者，账本本来就是平的；
  `rc_check` 证明的「每条返回路径上每个绑定恰好释放一次」对这里也成立。缺的是
  emitter 把自己造出来的中间值放进 unwind 看得见的地方，这跟刀 3 把 owned 绑定
  放进 `dawn_own` 是同一件事，只是当时漏了没名字的那一类。
- **改动面。** 方案 2 要在 `consume_all` 的常规路径上为每一行多个非原子操作数造
  `CSLet`，Core golden 全量漂移，最后使用分析与复用分析（`rc == 1` 的判断依赖实参
  直接交出）都要重新过一遍；方案 1 只改 emitter 的一个函数，Core 不动。
- **它恰好盖住两种出口。** 槽在 raise 和丢弃 continuation 两条路上都由同一个
  `dawn_own_drop` 释放，wasm32-wasi 上由影子栈释放，不用分别处理。

规则写在 `emit_ordered` 里：一行有两个以上会跑代码的操作数时（原来就是这时才
绑定临时变量），某个操作数若在消费位（`ks[i]`）、类型计数（`is_ref_ty`，字典除外）、
并且它**之后**还有会跑代码的操作数，就写成 `dawn_own[n] = <expr>;`，行里留下
`dawn_take(&dawn_own[n])`。槽号接在帧计数后面现取，不挂符号，所以不会和任何
绑定共享；`emit_fn` 按最终计数开 `DAWN_OWN_FRAME`，不用别的改动。其余情况仍是普通
临时变量：借用位是别人的引用（RC 已经把会产生 owned 值的借用操作数提升成 tracked
绑定，这就是 borrowed 形参调用、`++`、插值本来就干净的原因），标量不进账本，
最后一个会跑代码的操作数之后不再有代码能丢掉帧。

已命名的局部在消费位原来先被 `T t = dawn_take(&dawn_own[k]);` 取出槽，再等后面的
操作数（`R { a: a, c: boom("x") }` 就是这样漏的）。第一版把它从一个槽挪到另一个槽，
selfhost 的 C 里多出约 1.4 万处纯开销的槽间搬运，native 自编译慢了约 6%。终版不搬：
它本来就在槽里，`dawn_take` 推迟到使用处。这是安全的，因为 RC 只在本行其他操作数
都不提这个绑定时才把它判成转移（`consume_all` 与 `intr_args` 的 after-set 含其他
操作数的自由变量），后面的操作数若对它赋值，`snapshot_row` 会先把整行命名掉；
后面的操作数里若有 `return`，RC 在那里放的 drop 读到的也正是这个槽，比原来
（槽已被取空、值在 C 临时里）更对。

### 2.2 对 rc_check 预言机的影响

无。`rc_check` 读的是 RC 产出的 Core，这个修复没有改 Core 的任何节点；它断言的是
「控制流返回」时的平衡，而新槽在每条返回路径上都被 `dawn_take` 清空，cleanup
看到的是 NULL，和刀 3 对所有槽的约定一样。被修的是预言机按设计看不见的那一半
（unwind 路径），这一半的预言机是 spike-native 的 asan 检查和 wasm 的
`rc-balance`，所以回归语料落在那里。

### 2.3 验证

- spike-native 新增三条：`ordered_owned_raise`（record、tuple、ADT 构造、局部变量
  字段、owned 形参调用五种原先泄漏的形状，加 borrowed 形参、`++`、列表字面量、插值
  四种原本干净的形状，外加嵌套行与不 raise 的正常路径）、`ordered_owned_drop`
  （丢弃 continuation，无 panic）、`handler_arm_catch`（#458 原复现）。
  修前 LSan 分别报 135 字节/5 处、31 字节、328 字节/9 处，修后全部干净。
- wasm32-wasi（clang-20，`DAWN_RC_BALANCE=1`）：`rec`（issue 复现 A）、上面的形状合集、
  #458 复现的 `rc-balance` 修前 1、6、7，修后都是 0。丢弃 continuation 的形状在 wasm
  上不可跑（one-shot 恢复本来就不支持 wasm）。
- `scripts/native-asan-tests.sh` 的 `KNOWN_LEAKS[packages/tileir]` 修后跑干净，按脚本
  要求删除；全部 10 个单元在 ASan+UBSan 下通过。

### 2.4 代价（实测，2026-10-04，本机，与 origin/main `c96a1af8` 对比）

| 项 | 修前 | 修后 |
|---|---|---|
| native 自编译（dawnc-A 编 nmain，user 秒，6 次中位） | 11.3 | 11.6（+2.5%） |
| `native-fixpoint.sh` 墙钟 | 136.7 s | 141.1 s（+3%，噪声量级） |
| nmain 生成 C 体积 | 22,497,256 B | 22,399,006 B（−0.4%） |
| 带 `DAWN_OWN_FRAME` 的函数 | 3454 | 3595 |
| cc -O2 编 nmain | 53.4 s | 53.2 s |
| 分配密集基准（300 万次两字段记录构造 + 20 次 2^18 节点树，user 秒） | 0.53–0.56 | 0.50–0.59 |

C 体积反而变小，是因为推迟 take 省掉了原来「先取出槽再放进 C 临时」的那一行。
自编译那 2.5% 来自新开帧的 141 个函数和槽位落内存，在可接受范围内；第一版（局部也
搬槽）是 +6%，上面 2.1 已说明为什么改掉。

### 2.5 不做的（理由）

- 不在 RC 侧 A-normalize（方案 2）：理由见 2.1，Core 与 rc_check 不需要知道 C 的求值顺序补丁。
- 不回收行内槽位：槽在行的消费点执行之后才空，而消费点在调用方拼出的表达式里，
  emitter 在 `emit_ordered` 返回时还不知道它何时执行；嵌套行若复用会交叉。实测槽数
  增长的代价已在 2.4 内。
- 不改最后一个会跑代码的操作数之后的形状：那里没有东西能丢掉帧，生成的 C 不变。

## 三、分配先于会 raise 的实参（#482，2026-10-04）

§二 修的是行里**先**求值、后面还有代码要跑的 owned 操作数。#482 是反方向：被
帧持有、跨过实参求值的是**分配出来的对象**本身。`emit_alloc` 先调 `emit_ordered`
再写 `dawn_adt_new`，但一行里少于两个会跑代码的操作数时没有顺序可钉，那一个
操作数原样作为表达式串返回，于是调用文本落进了 `dawn_adt_new` 之后的字段写入：

```c
dawn_adt* t0 = dawn_adt_new(0, 2, UINT64_C(0x0000000000000003));
t0->fields[0].p = dawn_box_int(dawn_zz_1leak_1probe__boom(v1));
```

调用 panic 被 `catch_panic` 接住（或 fault 被 `catch_fault` 接住）时，`t0` 是普通 C
局部，强制 unwind 不认识它，对象泄漏。

### 3.1 同类点

逐个查了 emitter 里「先分配、后填入」的地方：

| 位置 | 结论 |
|---|---|
| `emit_alloc`（构造器、元组；记录更新由 `rc.rw` 改写成构造器后也走这里） | **漏**。修 |
| `emit_closure`（`dawn_clo_new` 后写捕获） | 今天不漏：RC pass 交来的捕获全是已绑定的名字（编译器自身 C 前后只有临时编号变化）。加同样的守卫防将来 |
| `cast` intrinsic（`dawn_adt_new` 后读操作数） | native 上不可达（`Object` 只来自 `use java`）。加同样的守卫 |
| 列表字面量（`CListLit`） | 不漏：元素不是叶子时 `rc.rw` 已改写成 `array_new` + 槽里的 `array_push`；剩下的全是叶子 |
| `CDictApply`、`emit_const_value` | 不漏：实参是字典或折叠常量，不跑代码 |

`Never` 类型的实参是另一种形状：`no_value` 让它留在行内（「它之后什么都不跑」），
但在分配里它之后**还有**字段写入，而之前已经有了分配。修前同样泄漏。

### 3.2 修法

`emit_alloc` 改调 `emit_alloc_row`，与 `emit_ordered` 共用一个循环，只多两条：

- 行内剩下的那个操作数，若 `inline_raises` 说它的文本会 raise（调用、intrinsic、
  Int 除法与取模，或这些出现在 box/dup/投影/一元/块尾里），先落 C 临时再分配；
- 不返回的操作数在分配前作为语句写出，字段里写零值（永远不会被读到）。

不会 raise 的实参（字面量、局部、dup、box、投影、普通算术）照旧行内，生成的 C 不变。
临时是普通 C 局部而不是槽：它和分配之间什么也不跑，和 `emit_ordered` 给最后一个
会跑代码的操作数普通临时是同一个理由。

### 3.3 验证

- spike-native 新增 `alloc_raise`：元组（issue 原程序）、记录、和类型构造器的后一个
  实参 panic，Int 除零作实参，`Never` 调用作实参，以及 `catch_fault` 接住的 fault
  作元组实参。修前 LSan 报 240 字节/6 处（六个形状各一处），修后干净。
- `emitc` 内联测试：元组的会 raise 实参先命名；不会 raise 的算术留在字段写入里，
  Int 除法先命名。
- JVM 侧不受影响：用父提交编出的编译器与修后编译器对十个 emit 目标做不遮蔽对照，
  逐字节相同，不需要 `Emit-Change`。

### 3.4 代价（实测，2026-10-04，本机，与父提交 `e89f6a46` 对比）

| 项 | 修前 | 修后 |
|---|---|---|
| native 自编译（两版 dawnc 编同一份 nmain，交替各 10 次，user 秒） | 最小 15.04，中位 16.81 | 最小 14.62，中位 15.87 |
| nmain 生成 C 体积（同一份源码） | 22,619,300 B / 377,064 行 | 22,631,346 B / 377,504 行（+0.05%） |
| 改动的分配点（临时编号归一后） | | 440 处各多一行 |

本机测时负载 12–14（另有写者在跑），自编译的差异在噪声之内，看不出代价；
#467 的 +2.5% 来自新开帧与槽位落内存，这里只多一个寄存器级的 C 临时，不开帧。

### 3.5 不做的（理由）

- 不把对象本身停进槽里再填字段：半成品对象的未写字段是垃圾，unwind 去 drop 它要先
  清零或改 mask，比先求实参贵，而且只为这一种形状改运行时约定不值。
- 不在 RC 侧把标量调用绑成 let：Core 与 `rc_check` 不需要知道 C 的求值顺序，理由同 §2.5。
- 不给 `inline_raises` 维护「哪些 intrinsic 不会失败」的白名单：intrinsic 一律当会
  raise，多出来的只是一个 C 临时，白名单却会在新增 intrinsic 时静默过期。
