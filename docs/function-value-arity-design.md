# 函数值的参数数量边界

> 状态：**current**。issue #87 的共享检查期参数数量边界。

## 问题与实测

父提交 `4963ca91` 的 JVM 只生成 Fn0 到 Fn9；函数值还有一个隐式证据包参数。
九个显式参数的普通效果操作能通过检查，却在运行时缺少 Fn10。
同一父编译器编译同一九参数效果程序，JVM 报 NoClassDefFoundError，
native 正确输出 45。因此 C 后端并没有相同的九参数边界，不能把两者说成同一种崩溃。
实测过程与父编译器哈希已记录在 issue #87 的认领评论。

## 方案与落点

按 issue 请求，在共享 checker 建立可移植的函数值上限：八个显式参数。
普通效果操作最终调用处理器闭包，也最多八个；控制效果处理器还接收续延，
所以操作本身最多七个。错误在声明或函数值形成处报告上限与实际数量，
不等到调用或运行时加载接口。JVM 接口生成与控制效果调度复用同一组常量。

检查函数类型引用、lambda、作为值使用的命名函数与构造器，以及效果操作声明。
命名函数直接调用和直接构造记录不是函数值，保持现有较宽参数支持；
不能在所有函数声明上粗暴加八参数限制，编译器自己的直接调用也需要它。

规范中文正本与英文译本同步说明边界。checker 语料钉住位置、数量、消息和 hint，
正控覆盖八参数函数值、八参数普通效果、七参数控制效果以及宽直接调用；
同一正控在 JVM/native 执行，超界程序在两个入口都必须以诊断拒绝。
Core golden 只通过官方 record/check 更新；另外核对真父编译器对同一新源码的输出。

## 验收记录

新增 checker case 固定七条超界诊断；官方 record/check 共 147 个 case、588 条诊断，
新增两处诊断调用点均覆盖，既有四处未覆盖项没有扩大。
七行运行正控在 JVM/native 与 ASan 下全部通过；610 项 selfhost、64 项 Planner、
两个后端自举固定点通过。Core 只经官方脚本重录并通过 17 份转储、88 个模块哈希检查。
最终格式化源码上的十项真父 JVM emit 比较全部逐字节相同，没有新增输出差异声明。

## 不做的

不按项目需要动态生成无限 Fn 接口，也不扩大控制效果调度器；这比提前诊断更大，
不是此次 issue 要求的低成本方案。不改 Java 本身的方法参数上限，不截断参数，
不把 C 的可执行结果记成运行时失败，不同时修改 #84 或 Playground #83。
