# tileiras wheel 缓存

> 状态：**current** —— issue #70 的缓存实现与首次 CI 热缓存观测。

修复前，四个 tile-golden 分片各自从包索引下载 toolchain.txt 固定的三个 wheel，网络超时会让尚未运行语料的分片失败。缓存只保存 wheel，键由 runner OS 与 toolchain.txt 内容摘要构成，不恢复虚拟环境，不设置跨版本回退键。

安装器接受可选 wheel 目录，省略时使用安装目录内的 .wheels。每次调用先核对固定版本对应的文件及 SHA-256，再决定能否复用已有安装；缓存命中不能绕过校验。缺失的 wheel 通过有重试上限和超时的 pip download 获取，安装始终用 --no-index --no-deps。安装后核对 Python 包版本及 tileiras 自报版本。

负控覆盖固定版本被改、哈希被改、缓存字节损坏，以及热缓存安装时禁止网络；工作流在分片一执行安装器契约。真实 pip 的九项契约和真实 CUDA wheel 的离线新虚拟环境安装均通过。

首次冷缓存运行 [33956181375](https://github.com/dawnop/dawn-lang/actions/runs/33956181375) 的分片 1/3/4 安装步骤分别为 8/7/9 秒，分片一的新增安装器契约为 12 秒。分片四成功，安装 9 秒、保存缓存 1 秒，完整 wheel 路径也落在 10 秒预留值内；它保存了 150,704,424 字节的 wheel 缓存。该运行其余未完成分片后来被取消，不作为完整作业的成功观测。

首次热缓存运行 [33956933580](https://github.com/dawnop/dawn-lang/actions/runs/33956933580) 使用提交 `5d29eab5`。下表时间取 Actions API 的步骤与作业起止时间（秒级），成功日志同时要求出现固定键的缓存命中和三个 wheel 的摘要检查：

安装步骤从冷缓存的 7–9 秒降到 6 秒，但缓存恢复和收尾也耗时，不能把安装步骤的缩短冒充完整作业的提速。预算取目前观测到的完整 wheel 路径最大值 10 秒（恢复 3 + 安装 6 + 收尾 1），分片一再计入冷、热两次观测的契约最大值 12 秒。保留原来的 checkout/toolchain 45 秒估计和内核本机观测 206/186/189/193 秒，按既有双倍规则得到 546/482/488/496 秒的规划值。四个既有上限 552/530/518/534 秒都更高，因此只回填依据，保留上限与 timeout，不为一次较快观测降低它们。

不做：缓存 venv（避免恢复平台与解释器状态）、宽松 restore-keys（避免混用固定版本）、修改 tile 语料或编译器输出（与网络问题无关）。
