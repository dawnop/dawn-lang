# The persistent work-item matrix for tile-golden, one name per line in run
# order: the kernels of `kernels=()` first, then the mutants in the order
# their blocks appear in run.sh. Both kinds live in one list because both cost
# real time, so a split by kind would leave one job carrying the slower half;
# round-robin over the mixed list spreads them, and the outliers with them.
#
# run.sh validates its executable list against this file in both directions at
# startup, and scripts/mutant-coverage/check.py holds the union of the CI
# shards to it. That checker says "mutant" throughout; it compares names and
# nothing else, so here read the word as "work item" -- a kernel missing from
# the union is exactly as unrun as a mutant missing from it.
#
# THE KERNEL ORDER IS NOT A LEVER, and knife 21 measured that rather than
# assuming it either way. Round-robin sharding reads positions off this file,
# so the order decides which shard runs what; what it cannot decide is how
# much that costs, because the kernels all cost the same.
#
# Per-item costs come from `ITEM_TIMES=<file> ./scripts/tile-golden/run.sh`
# on one full local run. Knife 21 took two of them, 2026-09-05, same tree,
# same tileiras, on a matrix of 141 items:
#
#   round 1, another agent building on the machine (load 6 to 9, falling):
#     126 kernels 4.35 to 6.04s (mean 5.35), 15 mutants 11.99 to 14.42s
#     (mean 13.80), 881s in total
#   round 2, machine quiet (load ~2):
#     126 kernels 4.09 to 4.66s (mean 4.30), 15 mutants 11.63 to 14.10s
#     (mean 13.65), 746s in total
#
# The two rounds agree about the MUTANTS (per-item correlation 0.96: a mutant
# that rebuilds more really does cost more) and say nothing whatever about
# the kernels (correlation 0.07, and round 1's cost-versus-position
# correlation is -0.58 -- the "expensive" kernels there are the ones that ran
# while the load was high, since the load fell during the run). On a quiet
# machine every kernel is within 0.6s of every other.
#
# Knife T2 took three more, and they say the same thing again. The first two
# were on 151 items (before knife T1 landed) and the third on the 154 the
# matrix holds today:
#
#   round 1, another agent building (load 7 to 26): 131 kernels 4.98 to
#     27.10s (mean 8.40), 20 mutants 15.44 to 24.53s (mean 18.36), 1484s
#   round 2, same tree, quieter (load ~5.5): 131 kernels 4.23 to 5.66s
#     (mean 4.85), 20 mutants 15.36 to 19.42s (mean 17.42), 1000s
#   round 3, rebased onto T1, machine IDLE (load 0.18 to 4.09): 133 kernels
#     4.30 to 5.54s (mean 4.64), 21 mutants 13.11 to 21.77s (mean 16.82),
#     984s
#
# The kernels' spread went from 5.4x to 1.3x between the first two rounds and
# the mutants' barely moved. Nothing here is a per-kernel property.
#
# What round 3 DOES say, and it is the one thing these rounds have found that
# is not load: a mutant costs more than knife 21 read. 16.82s against 13.65,
# and a mutant is a native rebuild of the package, so it is the item whose
# cost grows as the package does. gates.yml's four budget lines are restated
# from round 3's shard sums, 244.1 / 249.0 / 233.4 / 243.4s against 242.5 if
# it divided perfectly.
#
# So knife 20's dearest-first deal was reading load noise. It is left as it
# is, because reordering it would be reading the same noise the other way,
# and knife 21 appends its fifteen kernels at the end. What actually decided
# the split then was the fifteen mutants' fixed block order at the tail (they
# landed 4 / 3 / 4 / 4 with 141 items) and 126 mod 4. Measured round-2 shard
# sums: 193.1 / 179.3 / 185.0 / 189.0s against 186.6 if it divided perfectly.
#
# Knife T1 appended two kernels and one mutant, and the arithmetic came out
# EVEN for the first time: 144 items is 128 kernels and 16 mutants, 128 is
# 32 a shard and 16 is 4 a shard. Knife T2's five and five end that: 154
# items is 133 kernels and 21 mutants, and 21 mod 4 is 1, so shard 2 carries
# six mutants and the other three carry five. That one extra mutant is 16.8s
# and it is the whole of why shard 2 is the heaviest.
#
# Knife T3 appends six kernels and five mutants and the matrix is 165 items,
# 139 kernels and 26 mutants. Its own ITEM_TIMES round, 2026-09-05 on the
# rebased tree with the load between 1.1 and 3.3 (1084s unsharded):
#
#   139 kernels 4.42 to 5.74s (mean 4.67), 26 mutants 13.58 to 18.89s
#     (mean 16.15)
#
# which agrees with T2's round 3 on both, and confirms its finding a second
# time: the mutants are the item whose cost tracks the package, and the
# kernels do not differ. FOUR SHARDS NO LONGER FIT. Dealing 165 items into
# four is 277.2 / 262.2 / 261.4 / 268.8s, whose planning values are
# 694 / 664 / 663 / 678s and every one of them is over the 660s pole. Five
# is 214.4 / 208.9 / 210.2 / 215.3 / 220.9s, which is 569 / 558 / 560 / 571 /
# 582s, and gates.yml carries N = 5 from this knife on.
#
# Reordering these lines moves items between shards. That is harmless and the
# split is checked either way, but say so in the commit, and REMEASURE rather
# than shuffling by eye: knife 19 recorded four kernels as the dearest items
# here, knife 20's measurement said every mutant costs more than every
# kernel, and knife 21's said the kernels do not differ at all.
