## 一、判词概要：五条贯穿性根因

53 条发现背后反复出现同五个形状，先说结论：

1. **「一件事一份定义」在编译器自己身上没做完。** S1 把语义收成一份，但
   `eff_show`×3、`trait_method_sig`×2、`subst_subject`×2、`subject_key`×2、
   show 标量表×2、manifest 解析器×2、Maven 坐标×2、CLI 失败外壳×2（且已漂移）、
   四份 `*_at` 派生骨架、六份 Core 手写遍历、三份 intrinsic 字符串分发——全是
   native-plan §11.3 点名的根因，只是没扫到自己（RC-02/03/05/07/08/12，RP-12）。
2. **spec 的「normative」地位与其失真程度不匹配。** §11 记着三个不存在的模块
   （`core/math`/`core/option`/`core/result`）、25 行内自相矛盾、漏报真实存在的函数
   （`str.replace` 被 19 处逐字重写）；§1.4 关键字表漏 `return/break/continue`；
   §10.2 与 §11 对重复 `use` 的说法相反；`Never` 是规范词汇但类型位写不出（RD-13、RP-10、RX-09/11/12）。
3. **双后端一致性靠「碰巧」的面比记录在案的大。** Float 渲染/解析、移位、`to_int`、
   `show`、`decode` 的 charset 域、Unicode 数字——每条都有最小区分程序；且
   已写下的缺口在互相豁免（「Float 已排除在语料外」被用来豁免 parse_float），
   缺口在自我繁殖（RP-01..05）。
4. **可见性/累积模型漏了半张表。** trait impl 表不随模块累积（用户 trait 是单文件特性）；
   `internal` 内建集漏了 `io_*`/`bytes_*`/`str_lower/upper`，用户一行裸调用即可
   绕过整个 Result 错误模型直face JVM 栈迹（RX-01、RD-02）。
5. **std 的 API 缺口在反向污染用户代码。** 缺 `strip_prefix` → 33 处魔法整数偏移；
   缺 `contains/any/all` → 31 条 `||` 链 + 两份逐字相同的手写 `contains`；缺
   hex/base64 → 8 份手搓 hex + `use java` 把鉴权链钉在 JVM、纯函数染成 `!io`（RD-03/05/08/10）。

## 二、纯洁性（RP）

### RP-01 [复] `to_string(Float)` 三处三答案，C 后端自认不合规
`emit.dawn:2387`（JVM=`Double.toString` 最短往返）、`runtime/c/dawn_rt.c:456`
（`%.17g`，注释自陈 NOT byte-identical，`nan`/`inf` 拼写也不同）、`interp.dawn:244`
（comptime 委托宿主 JVM）。`to_string(0.1)`：JVM/comptime `0.1`，native
`0.10000000000000001`。更坏：`const S = to_string(0.1)` 被 JVM 宿主折成 `"0.1"`
烤进 native 二进制——与 `dawn_rt.c:1062` 已修过一次的大小写折叠 bug 同一形状。
「Float 排除在差分语料外」的缓解已过期（Phase 6 已出口，语料只测碰巧一致的值）。
spec §4.3:535 把语言级答案定义成 JVM 方法名（`Double.toString` 的行为还随 JDK 版本变）。
**方向**：语言自己的 dtoa（Ryū/Grisu）两后端共领一份；spec 改「最短往返 + 明确 NaN/Inf 拼写」。严重度：高。

### RP-02 [复] `show` intrinsic 三路分叉：C 编译期 panic、comptime 静默答错
> **已修（2026-07-30）**：修法与发现记录不同，见下方「落地回填」。
`lower.dawn:1589` 对非 expandable 且无 provided impl 的类型（`Bytes`/`Array`/`Fn`/未解
TyVar）发 `CIntrinsic("show")`。JVM 正常；**emitc 无 `show` 臂** → `panic("intrinsic
not implemented for native")`——JVM 能编的程序 native 在 codegen 崩；interp 把 `show`
并进 `to_string` 臂，`VStr` 不加引号、容器返回字面串 `"<value>"`，违反 `lower.dawn:1544`
写明的嵌套渲染契约（String 要带引号）。**方向**：emitc 补臂或明确拒绝；interp 拆
`show`/`to_string` 两臂。严重度：高。

### RP-03 [复] 移位与 `to_int` 把 spec 的「保证」交给 C 的 UB
> **已修（2026-07-30）**：见下方「落地回填」。
spec §4.3:510「移位计数取低 6 位（同 JVM LSHL）」标为**保证**；`emitc.dawn:684` 的
`CUshr` 无掩码，`CShl/CShr` 落通用臂——计数 ≥64/负数是 C11 UB，x86-64 碰巧掩码、
AArch64 给 0。`to_int`（`emitc.dawn:1010`）裸 `(int64_t)` 转换 vs JVM `D2L` 饱和语义：
`to_int(0.0/0.0)` JVM=0、native=INT64_MIN。CI 只跑 x86-64 所以恰好绿。
**方向**：三个移位发 `& 63`；`to_int` 走显式饱和的运行时函数；两条进 spike-native 语料。严重度：高。

### RP-04 `bytes.decode` 的定义域一边是宿主 charset 注册表、一边是两个条目
`std/bytes.dawn:67` 是纯函数；JVM 实现 `new String(byte[], String)`（定义域=宿主
provider 全集），C 实现只认 UTF-8/UTF8/ISO-8859-1/latin1（`dawn_rt.c:1313`）。
`decode(b, "UTF-16")`：JVM 返回字符串、native panic。spec 没有一句说哪些 charset 存在。
**方向**：语言定义的封闭 charset 集合，两后端各自实现。严重度：高。

### RP-05 `parse_int`/`parse_float` 接受语言分叉，且缺口互相豁免
JVM `Long.parseLong` 经 `Character.digit` 接受非 ASCII Unicode 数字（`parse_int("١٢٣")`
= `Some(123)`），C 的 `dawn_digit_val` 只认 ASCII（`dawn_rt.c:1120`）。`parse_float`：
strtod 收 hex float、Java 收尾缀 `f/F/d/D` 与 `"Infinity"`——C 源注释自己写「Floats are
already out of the differential corpus over dawn_str_of_float; this is the same gap」，
**用 RP-01 的缺口豁免自己**（native-plan §14 总结过的机制：「写下来的缺口让人不再看它旁边」）。
是 native-plan:1480 那条（space 修剪，实际一致）旁边**没记**的真分叉。
**方向**：接受语言写成 spec 里的一条 EBNF，两后端各自实现。严重度：中。

### RP-06 `String` 的序是 UTF-16 码元序，其他一切是码点
`str.len`/`substring`/`chars` 全线码点；`<`/`cmp`/`sort` 是 `String.compareTo` 的
UTF-16 码元序，C 端专门造了 UTF-16 迭代器复刻（`dawn_rt.c:512,635`），还保留幅值
（`cmp("a","z")` 答 `-25`，一个可打印的宿主量）。非 BMP 反例：`from_code_points([0x1F600])
< from_code_points([0xFFFD])` 为 true（UTF-16 序）而码点序为 false。另 `emitc.dawn:673`
注释称 code-point order，与 `dawn_cmp_str` 自述矛盾。两后端一致，故是概念病不是错答案。
**方向**：`Ord[String]` 定码点序、`cmp` 只承诺符号；UTF-16 只活在 `use java` 边界。严重度：中。

### RP-07 语言级 `hash` 的定义就是 JDK 的算法
spec §9.5:1012 拿 `Arrays.hashCode` 当定义；C 端复刻有符号 byte 折叠、1231/1237
（`dawn_rt.c:598`）。另两处「语言已删、运行时仍在」：`Hash[Float]`/`Ord[Float]` 已从
标量表删除，但 `dawn_hash_float`/`dawn_cmp_float` 还在（`dawn_rt.c:586,624`）——哪天有人
把 `Ord[Float]` 加回来，静默拿到 `Double.compare` 全序，正是 spec §4.3 花七行拒绝的东西。
**方向**：hash 算法写进 spec（不引用 JDK）或声明未指定；删两个孤儿原语。严重度：中。

### RP-08 [跑] `Buf` 的值语义由后端别名分析兑现，类型系统无保证
`std/bytes.dawn:29`：`put` 是纯函数，引用透明性靠「`array_push` 恰在唯一读者时原地扩展」
这条**后端条款**，两后端用两套不同机制维护（native=Perceus、JVM 无 RC）。std 调研的
实跑显示当前别名场景安全（`put(a,66)`/`put(a,67)` 各得独立结果）——即**今天没有错答案**，
但这是 spec §6.2.4 纯性保证在 std 内唯一一处依赖优化前提的地方，且没有对拍钉住。
**方向**：加共享分叉对拍语料；把前提从注释升格为契约。严重度：中（前提被破则高）。

### RP-09 std/io 的 Err 载荷就是 JVM 异常 `toString()`，spec 教用户前缀匹配它
`std/io.dawn:16` 头注释把「`Err` = 异常 `toString()` 逐字节」写成设计；九个 io 函数的
`Err(String)` 都是 `java.nio.file.NoSuchFileException: /x` 形状；spec §9.8:1076 明文
「需要区分异常种类时按前缀匹配字符串」。native 没有 `Throwable.toString()`，同一失败
Err 文本必然不同——错误分支不可移植。**已追踪项的新侧面**：error-model A 收的是
ForeignError 类型定义；没覆盖「泄漏已在 std 公开 API 返回值里」。
**方向**：并入 #86（error-model A），std 自产错误改 std 定义的形状。严重度：中高。

### RP-10 [复] spec §11 的 `core/math` 不存在，且是「std 用 unsafe_pure 包 java」的最后一处现行陈述
`spec.md:1314` 写 `core/math`（`sin cos sqrt pow ...`，「内部以 unsafe_pure 包装
java.lang.Math」）；`std/modules.txt` 无 math，`sqrt/sin/cos/pow` 全仓零实现，§13 的
`dist` 示例照抄编不过。与 §6.4（LANG-01 关账后重写，「std 一处 unsafe_pure 都没有」）
直接冲突。同时暴露真缺口：超越函数一旦要加，`Math.sin` vs libm 差 1 ulp 就是 RP-01 类
分叉——**现在是加之前定契约的唯一时机**。**方向**：删 §11 该条与 §13 示例；加数学库前
先裁决权威实现。严重度：中。并入 RD-13 的 spec §11 重写。

### RP-11 comptime 能力边界=「解释器缺哪个原语」，spec 复述的清单已漂移
spec §7.2.2 把「Map/Set 不可 comptime」当语言规则写；实际拒绝集合更宽（`hash`/`cmp`/
`cast`/`array_*`/`bytes_*`/`popcount`/`catch_*` 皆无臂，`CValue` 无 `VBytes`），
`const XS = list.sort(...)` 编不过而 spec 未记。§7.2.4「comptime 无 Java 互操作（由约束 1
自动保证）」与 §6.4 的 `--comptime-ffi` 矛盾，且「自动保证」推导不成立。
**方向**：`types.intrinsics()` 加 `comptime: Bool` 列，spec 引表不复述；§7.2.4 补例外。严重度：中。

### RP-12 interp 是三个原语分发器里唯一不读共享表的（RP-02/11 的机制根因）
`emit.dawn:628`/`emitc.dawn:934` 都从 `types.intrinsics()` 查符号；`interp.dawn:584`
是 204 行手写 `else if` 链。双向死代码：interp 有臂无生产者（`map_index`/`chars`/`split`
——后两个还是 std 化后同一函数的第二份定义，走宿主实现）；emit 仍派 `starts_with`/
`ends_with` 给 `String.startsWith`（`emit.dawn:2399`，`stdlib.dawn:94` 已标迁出），emitc
正确地没有。`types.dawn:1242` 已示范表与实现的对拍门禁，没有一条覆盖 interp。
**方向**：一条测试——`intrinsics()` 每个名字要么 interp 有臂、要么在显式 comptime 拒绝表上，
两表之外为空。严重度：中（撬动面大）。

> **已修**（`fix/rp12rc09-interp-gate`，与 RC-09 同一提交）。落地形态与复审的描述有三处
> 值得记下来：
>
> 1. **「有臂」不靠维护第二份名单来判定，靠调用**。测试拿**空参数**调 `call_builtin`：
>    凡是读 `args[0]` 的臂都会在空列表上 panic，而 panic 恰好就是「控制流进了某条臂」
>    的证据。于是不必给每条臂编一组像样的实参，日后新增的臂也不用回来改探针。
> 2. **`interp_arms()` 放在 if 链前面当闸，不是并排放一份拷贝**。名单外的名字进不了任何
>    臂，所以「未申报的臂」是构造性死代码而非隐形活代码；而漏申报也不会静默——名字若是
>    intrinsic，划分检查就红。
> 3. 拒绝集合实测 **59 个名字**，spec §7.2.2 用散文答的那半（Map/Set）只占 17 个。
>    59 个连同分组理由写在 `comptime_rejects()` 里，供 RP-11 的 spec 重写引用。

## 三、语法表面（RX）

### RX-01 [复] 用户 trait 只在声明模块内可用——impl 表不跨模块累积
spec §3.5 承诺「impl 全局生效，不需要 use」。实测（主线独立复现）：`lib.dawn` 里
`pub trait Sizey[T]` + `pub type Box` + `impl Sizey[Box]`，跨模块 `lib.describe(Box{n:5})`
报 `no impl of Sizey for Box`，hint 教你做的正是已经做了的事。根因 `analyze.dawn:996`：
每模块 `Cx` 只播种 `impl_table: std.impls`，`exports` 逐模块累积而 impl 没有。另一半：
trait 方法作为「模块函数」没有 `pub` 语法可导出。全仓 7 个用户 trait 恰好无一跨模块用，
所以从未被踩到。**这是本轮最高优先级的语言 bug**：抽象特性只在单文件成立。
**方向**：impl 表随 exports 在 `analyze_program` 累积；trait 方法导出定拼写进 §3.3。
严重度：高；纯放宽，不破坏。

> **已修（`fix/rx01-trait-crossmodule`）。** `analyze_program` 现在像累积 `exports`
> 一样逐模块累积 impl 表。三件与复审判断不同的地方，记在这里免得下次重查：
>
> 1. **波及面比记录的大。** 不只用户 trait：`pub type ... derive Show` 的 impl 同样
>    只在声明模块生效，跨模块 `to_string(imported)` 报 `no impl of Show`。四个预置
>    trait 都在这条路上。
> 2. **只有 checker 看到的是分模块视图**，lowering 的 `program_tables` 一直在合并
>    所有模块的表。所以这是**误拒**而非误编译，修完 emit 字节零变化（prev-diff 全绿，
>    Core golden 只有 `analyze` 自己的哈希动）。
> 3. **「trait 方法没有 pub 语法可导出」这半条是错的。** `exports_of` 早就把 pub trait
>    的方法当 pub fn 放进 `ModExports.fns`。四种跨模块拼写现在都通：`lib.describe(box)`
>    （泛型入口）、`lib.sizey(box)`（别名直呼）、`use lib.{sizey}` 后裸调、UFCS
>    `box.sizey()`。**§3.3 无需补拼写裁决，无遗留项。**
>
> 顺带确认的一条规则（测试里写了）：**跨模块重复 impl 由孤儿规则报，不由一致性检查报**，
> 而且永远如此——两个不同模块要都能合法写同一个 impl，就得互相 import，加载器判环。
> 一致性检查拿到全程序视图是第二道防线，不是新的报错路径。

### RX-02 [跑] 模块别名与值同占命名空间：`use std/map` 后 `map` 不能当参数名
`use std/map` + `fn count(map: Map...)` → `error: map shadows the imported module`。
被作废的都是最自然的名字（map/set/list/str/io）；std 自己全用 `m`，全仓 18 处 `m: Map`
零处 `map: Map`。且远距离生效：文件顶加一行 use，几百行外同名局部变量编译不过。
**方向**：模块别名独立命名空间，冲突降级为局部遮蔽。严重度：中。

### RX-03 遮蔽是模块级全量的，且没有限定逃生舱
spec §10.3「被遮蔽的拼写在该模块不可达」；Rust 敢这样是因为有 `::` 路径，Dawn 没有。
`std/str.dawn:126` 是原告陈述：因为 `len` 被 str.len 遮蔽，写不出列表 `len`，凭空多出
`slice_cps`/`pad_fill`/`rev_cps` 三个只做带下标递归的私有函数。
**方向**：给内建/prelude 一个可限定拼写（`std/list` 导出 `list.len` 即可）。严重度：中高。

### RX-04 `for` 头只收裸名字，`let` 却收模式——遍历 Map 永远两行
`for (k, v) in entries(m)` → parse error（`parser.dawn:1028` 只收 IDENT）；全仓 27+ 处
`for pr in ... { let (k, v) = pr }`，`pr`/`sm` 这类名字是缺口的化石。
**方向**：`for <不可反驳模式> in e`，复用 `let` 的模式解析器。严重度：中；纯放宽。

### RX-05 「不得静默丢弃」按语法节点开洞，不按类型
`checker.dawn:6037` 豁免绑在「表达式是不是 Java 调用节点」：`sb.append("a")` 裸着丢合法，
包进 `if` 两臂就报 discard；把 `Files.exists` 抽成 Dawn 包装函数，调用点全要补 `let _ =`。
类型没变，变的是谁生产了它——重构改变安全规则的判定。
**方向**：豁免挂到类型上（不透明 Java 引用），或取消豁免配专门诊断。严重度：中；收紧是破坏性。

### RX-06 [复] `<` 在 Float 上能用，`[T: Ord]` 不能——同一运算两套定义
`1.5 < 2.5` = true；`smaller[T: Ord](1.5, 2.5)` → `no impl of Ord for Float`。函数体
逐字合法、泛化一次就用不到具体类型。spec §4.3「原生有序」旁路正是分家点。07-26 裁决的
是「Float 不给 Ord」，没裁决 `<` 与 bound 就此分家的后果。
**方向**：spec 把两套规则并列写清（今天混写），或 Float 给 Ord（NaN 语义写死）让 `<` 一律走 cmp。
严重度：中；后者破坏。

### RX-07 带 bound 的函数不能作函数值，std 自己在包 lambda
`map(xs, to_string)` → `cannot be used as a value`，hint 教写 `fn(x) => to_string(x)`。
`to_string/cmp/hash/show` 恰是最常传的函数；`std/list.dawn:133` 的 `sort` 就是这个补丁
（`sort_by(xs, fn(a,b) => cmp(a,b))`）。**方向**：调用点可定型时固化字典生成已应用闭包
——字典传递天然能做。严重度：中；纯放宽。

### RX-08 `type X = Int` 报错、`opaque type X = Int` 合法——关键字预测不了右侧
三个声明形式里，形状相同的两个（`alias N = T`/`opaque type N = T`）用不同关键字，形状
不同的两个（`type` 的 ADT / `opaque type` 的 `= T`）用同一个。parser 专备的 hint 是墙存在
的证据。LANG-05 结案时没回头看三个关键字的关系。**方向**：透明度做成修饰词
（`alias`/`opaque alias`，或 `type` 两者都收）。严重度：中；改拼写破坏。

### RX-09 [复] `Never` 是规范词汇 + 有字节码映射，但类型位写不出
spec §4.7/§8.2/§12.2 都用 `Never`；`fn boom() -> Never` → `unknown type: Never`，hint
的内建清单漏 `Bytes/Map/Set/Option/Result`，还教用户 `type Never = ...`（会得到无关 ADT）。
**方向**：注册为不可重定义的内建类型名（只许返回位）；修 hint。严重度：低；纯放宽。

### RX-10 效果变量在 `alias` 硬拒、在 record 字段放行且语义未定义
`alias Mapper[T,U] = fn(T) -> U !e` → error；`type Box = { f: fn(Int) -> Int !e }` 编译
通过但退化（调用被判「未声明 !e」，哪怕调用方声明了）。根因：§6.3 效果变量只在**签名**
中引入，record 声明不是签名，那个 `!e` 没有绑定者。语言有效果多态，却没法给效果多态的
类型起名字。**方向**：类型参数列表接受效果参数，或两处同拒同 hint——不能一硬错一静默。
严重度：中。

### RX-11 `java` 是硬保留字，而 `as/derive/opaque` 都是上下文关键字
`token.dawn:192`。`let java = 1`、record 字段 `java:` 都报错，报错还不说「这是关键字」。
`use c` 已在 native 计划里——照今天的做法第二个宿主会再吃掉一个单字母标识符。顺带：
spec §1.4 关键字表漏了 `return/break/continue`（token.dawn:202 三个都保留）。
**方向**：`java` 降为上下文关键字（只在 `use` 后特殊）；补全 §1.4。严重度：低中；纯放宽。

### RX-12 `use m` 与 `use m.{T}` 必须同时写，spec §10.2 却说重复 use 是错误
§10.2「二选一，重复是错误」vs §11「除 use std/cursor 外还要 use std/cursor.{Cursor}」；
实现站后者（`analyze.dawn:840` 专门特判不算重复）。真实站点：`std/str.dawn:28-29`、
json 的 lexer/parser。最普通的模块形状（函数+类型都导出）对应最丑的导入。
**方向**：`use m` 顺带把 pub 类型带进类型位置（LANG-06 的 `m.T` 已承认模块限定覆盖类型），
改掉 §10.2。严重度：中。

### RX-13 「名字搬走了」的 hint 按裸短名建表，系统性指错模块
`stdlib.dawn:181` 按 modules.txt 顺序逐模块覆盖、后来者赢：`size` 指 std/set（该指
std/map 时也指 set）、`slice`/`empty` 指 **std/pvec**——内部实现模块，§10.6 公开清单里
没有它。报错在最需要指路时指错路，还指向不该依赖的模块。
**方向**：`moved` 值改候选列表；pvec/hamt 排除出建议来源。严重度：中。

## 四、编译器结构（RC）

### RC-01 [复] 静态表按「每查询重建一次」使用；注释宣称已修的正是没修的

### RC-02 lower 里四份平行的派生关系骨架（eq/cmp/hash/show）

### RC-03 Core 无通用遍历器：6+ 份手写全树遍历，最危险的那份不 exhaustive

> **2026-07-30 最小版已修**（`756b7a9`，随 RC-04 一并）：`fv_expr` 全枚举（补 10 个叶子，

### RD-04 两套位置货币（码点 Int 与 opaque Cursor）之间没有桥

## 八、落地回填：RP-02 + RP-03（2026-07-30）

triage §六 A 的第 2 条已做（提交 `59363f7` 移位与 `to_int`、`b9e3057` 渲染）。
回填两件与发现记录不一致的事，以及一件发现记录没料到的。

**RP-03 照方向做了，另外补了一处发现记录没提的 UB。** 三个移位都发掩码后的计数；
`to_int` 走新的 `dawn_int_of_float`（饱和，放在 `dawn_idiv`/`dawn_imod` 旁边）。
多做的一处：`<<` 除掩码外还要经 uint64_t——把位移进有符号类型的符号位本身就是 UB
（C11 6.5.7p4），而 `1 << 63` 是 Dawn 定义了的值（Int 环绕，即 `Int.MIN`）。
`>>` 保持有符号，因为符号扩展正是算术右移承诺的东西。
spec §4.3 顺手补了 `to_int` 的那条：移位规则是**写了没实现**，饱和语义是**根本没写**。

**RP-02 的修法不是「emitc 补臂」，因为擦除本身就是那个缺陷。** 实测确认
`CIntrinsic("show")` **今天只有一个生产者：`Bytes`**（把 `lower.dawn:1589` 改成 panic，
再编 selfhost / site / 四个 package / playground / 整个差分语料，一次都没打到；
`Array`/`Fn`/未解 TyVar 全被 checker 先挡住，`List`/`Map`/`Set` 自 S3 起走 std 的条件 impl）。
而 `show_scalars()` 承诺语言自己渲染五个标量，其中四个各有一个具名 intrinsic
（`str_of_int`/`str_of_float`/`str_of_bool`/`quote`），只有 Bytes 掉进擦除的那条末路。
擦除是不可实现的：native 的擦除槽是一个 `void*` 加一个 kind 标签，标签只说「是个 ADT」，
永远说不出是哪个，所以 JVM 那条 instanceof 链在 native 没有对应物。
故修法是 **lowering 给 Bytes 发 `str_of_bytes`**，两个后端各一条平臂。
渲染结果不变（spec §9.5.1 早就写了 `<N bytes>`），JVM 字节码也不变（`byte[]` 本就是
Object，装箱是空操作），六个 `emit *` label 对 v0.31.0 全绿——**所以这不是 Emit-Change**。

**`show` 的臂留着，emitc 那条是拒绝而不是实现。** 今天没有生产者，但删掉它会把
「这份枚举没料到的类型」从「JVM 有个尽力而为的答案、native 明确拒绝」变成
**两个后端一起 panic**。代价不对称，所以留。拒绝时点名类型（从 CBox 读回来——擦除之后
只有那儿还留着它）。

**interp 那半是错答案，不是崩。** `show` 与 `to_string` 共用一臂，而两者唯一的区别
（`to_string("a")` 是 `a`、`show("a")` 是 `"a"`）恰好是一条臂表达不了的东西；非标量折成
字面串 `"<value>"`。拆成 `show_value`：String 加引号、认不出的**拒绝**。
今天 Core 到不了这条臂，所以它的门禁是单测而非语料；`const_fold.dawn` 另补了确实
经过 Core 的那对（顶层裸、嵌套带引号）。

**新语料两个**：`int_edges.dawn`（移位计数取低 6 位 / `to_int` 饱和，只打印 Int 与 Bool，
避开 RP-01 的 Float 渲染分叉）、`show_bytes.dawn`（Bytes 在六个位置各渲染一次）。
