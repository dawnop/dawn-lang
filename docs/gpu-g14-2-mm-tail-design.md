# GPU G14-2 第二刀：matmul 与 GEMM 工厂的尾块

> 状态：**current**（进行中）。第一刀（越界语义探针，PR #980）已合并，结论是方案 A 成立；本刀只放宽 matmul 族工厂的
> 整除守卫。依据：补裁一第 2、5 条（读侧 PadZero、写侧依赖 view 越界屏蔽、K 循环上整除且在宿主端算；整除形状设备字节逐字节不变）。
> FA 尾块与 bias 广播和 FA 的交互不在本刀。

## 1. 前提（已由前序工作确认）

- `cells` 本来就支持静态 extent 的尾块：网格是各维上整除，读侧 `pad` 缺省 `PadZero`，写侧靠 partition view 的越界屏蔽。
  拒绝非整除的只有工厂里的三条守卫（`mm_record`、`mm_domain`）和下整的 K 循环上界。
- 第一刀三卡实测：二维两轴同时越界的 store 被屏蔽；非 16 字节倍数的行跨距（f16、N=999）汇编通过且数值精确，所以
  **不加跨距守卫**；K 尾在 f16/i8/bf16 上与主机参考逐 lane 精确。
- 第一刀的探针 tile 固定为 32x32x32。本刀要补的是**各架构真实计划**上的尾块：sm_90 的 128x128x64 与 sm_100 的
  256x128x128 加 cga=2，两者的 TMA 路径可能与 32 的不同。

## 2. 改什么

三个函数改动，其余不动：

1. `mm_record`、`mm_domain`：删除 `m % tm`、`n % tn`、`k % tk` 三条整除守卫，保留「正数」。panic 文案收窄为
   `matmul: dimensions must be positive`。
2. K 循环上界：`mm_body`、`mm_f16_body`、`mm_i8_body`、`gemm_acc_loop` 四处 `shape.k / cfg.tk` 改为宿主端的
   `k_blocks(shape.k, cfg.tk)`（上整除）。`shape.k` 是宿主 `Int`，所以整除时折成同一个整数常量，
   记录出的字节码不变；这是本刀的硬判据，由全部既有 golden 逐字节验证。
3. 读侧：`cells` 的 `pad` 缺省 `PadZero`，不改。K 尾上两个操作数都填 0，MMA 累加 0×0。写侧：输出 `cells` 的 extent 用真实 M、N，
   越界 lane 由方言屏蔽。bias 行（`[1, N]`）同走 `cells`，N 尾上越界列读 0，对应的输出 lane 被屏蔽，所以不污染输出。

不新增 `cells` 参数、不新增 tileir 公开面。

## 3. 验证

### 3.1 黄金（既有字节不变，新增尾块字节）

既有 256+ 个 golden 的 `.mlir` 与 `.tilebc` 在 JVM 与原生两个后端上必须逐字节不变（任何变化即停，回交）；
`--config-manifest` 输出与改前逐字节相同。新增 golden（尾块形状 301x203x299，三维都不整除）：

| kernel | 内容 |
|---|---|
| `matmul_tail` | f64 通用计划 |
| `matmul_f16_tail`、`_sm90`、`_sm100` | f16 三个计划 |
| `matmul_i8_tail_sm100` | i8、sm_100 计划 |
| `gemm_bf16_tail`、`_sm90`、`_sm100` | bf16 到 f32 恒等 epilogue |
| `gemm_bias_relu_bf16_tail`、`_sm100` | 偏置加 relu 转 bf16，N 尾上的偏置读 |

### 3.2 设备（tile-gpu-diff 新家族 `mmtail`）

每张卡用自己架构的计划，对 f64、f16、i8、bf16 到 f32 与 bias 融合各跑一次尾块形状，
主机侧算期望整缓冲：输出缓冲比 M×N 多留哨兵，操作数缓冲在数据后接毒值（浮点 +inf，i8 为 127），
判据是整缓冲逐 lane 相等（含哨兵）。语料为小整数或二进制小数，任意累加顺序都精确。

### 3.3 负控（每条先证明会红）

| 变异体 | 做法 | 预期 |
|---|---|---|
| `mm-tail-k-floor` | K 循环退回下整 | K 尾被丢，数值错，设备红 |
| `mm-tail-no-pad` | f16 操作数读侧 pad 改成 `NoPadding`（未指定值） | K 尾与 M 尾读到未指定值，设备红（见 §4） |
| `mm-tail-out-roundup` | 输出 extent 上整到 tile | 越界写生效，哨兵被覆盖，设备红 |

三者都是合法录制，在 tile-golden 里确认「黄金文本与字节在两后端都变」，在 tile-gpu-diff 里确认「cubin 能装能启动，
被具名参照物拒绝」。另有守卫拒绝用例：非正数形状仍 panic，消息固定（`mm_config_check`）。

## 4. 取舍与实测后修订

- 第一刀没做的 `NoPadding` 负控本刀做了：sm_86 上 f16 的 `mm-tail-no-pad` 在 126063 个 lane 里有 6322 个不同、333 个非有限，
  即未指定值在设备上并非恰好是零，毒值被读进去了，所以不需要另选一个非零 pad，直接用 `NoPadding` 当变异体。
  这同时说明 `PadZero` 不是可有可无的缺省：K 尾上它是正确性条件。
- 设备用例的形状取 301x203x299：三个维度在 sm_90 的 128x128x64 与 sm_100 的 256x128x128 上都不整除，且 N、K 的字节跨距
  （16 位 406、598 字节，8 位 203、299 字节）都不是 16 的倍数，沿用第一刀的结论（不加跨距守卫）并在大 tile 计划上复验。
- 输出缓冲后接 320 行哨兵：最大的行块是 256 行，所以不屏蔽的越界写必落在哨兵上。

## 5. 不做的（理由）

- **FA 尾块**：K/V 侧要 `-inf` 掩码、改 online softmax 数值路径，风险最高，另成一刀，允许推翻。
- **FA 与 bias 广播的交互**：不在本刀。
- **新增 `cells` 参数或 `tail=` 开关**：尾块是 extent 不整除的自然结果，加开关是平行真相。
- **主体加尾块的双路径（方案 B）**：view 的掩码在方言里，拆开没有实测收益，且每个形状多份设备码。
- **调用方补零（方案 C）**：把 view 已有的能力推给调用者。
- **16 字节行跨距守卫**：第一刀实测三卡汇编与数值都通过，不为不存在的拒绝造守卫；若本刀在大 tile 计划上发现拒绝，
  再按实测补守卫并写进文案。
- **`NoPadding` 的尾块**：未指定值在 K 归约里会污染，只有写后丢弃的 lane 才可用。
- **新计划测量**：沿用既有计划格，不对尾块形状做任何速度断言。
- **动态 extent（`DYN_DIM`）的尾块**：其定义就是无尾块，尾块要静态 extent。
